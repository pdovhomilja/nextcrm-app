title: Background jobs
description: How NextCRM uses Inngest for events, scheduled jobs and long-running work.
---

Slow, external or scheduled work runs in [Inngest](https://www.inngest.com/) functions. Request code sends an event and returns. Inngest calls the app back at `/api/inngest` to run the function, with retries.

## Pieces

| File | Role |
| --- | --- |
| `inngest/client.ts` | The Inngest client. Reads `INNGEST_ID`, `INNGEST_APP_NAME`, `INNGEST_EVENT_KEY`, `INNGEST_SIGNING_KEY`. |
| `inngest/functions/` | One file per function, grouped by area. |
| `inngest/lib/` | Shared helpers (embeddings, IMAP). |
| `app/api/inngest/route.ts` | The `serve()` endpoint. Every function must be listed here. |
| `lib/plugins/inngest.ts` | Builds functions for plugin crons, event handlers and after-actions. |

## Run it locally

```bash
pnpm inngest:up   # dev server on http://localhost:8288
pnpm dev
```

Set `INNGEST_DEV=1` in `.env.local` so the SDK uses the dev server. The dev server syncs only `http://host.docker.internal:3000/api/inngest`. Open the dashboard to see registered functions, send test events and inspect runs. See [Local setup](/docs/developers/local-setup).

Sending or scheduling a campaign (UI or MCP `campaigns_send`), and MCP `campaigns_resume`, is refused before any status change or event if the campaign has no step 0 (MCP returns a `CONFLICT` error). Of two simultaneous send calls (UI or `campaigns_send`) only the one whose conditional status write changed the campaign emits `campaigns/send-now`; the other gets the same refusal as a campaign already sending.

A campaign goes from `sending` to `sent` (and gets `sent_at`) once step 0 is finished: no step-0 send is still `queued` or `sending`. Queued sends to recipients who unsubscribed or are globally suppressed do not count, since `campaign-send-step` skips them without updating the row; `failed` counts as finished. `campaign-send-step` checks this after each send or skip, `campaign-send-now` and `campaign-schedule-send` after the fan-out (a campaign with no recipients becomes `sent` there). Only a `sending` campaign moves, so a paused or deleted one stays as it is. Follow-ups still go out after the campaign is `sent`.

One send row produces one email. `campaign-send-step` moves the row from `queued` or `failed` to `sending` with a conditional write before it calls Resend, so of two overlapping runs (a resume fans out every send again) only one emails; the other skips. The Resend call carries the idempotency key `campaign-send/<sendId>`: a retry after Resend already accepted the mail gets the first response back instead of sending again. Resend keeps a key for 24 hours and stores only accepted requests, so a send it refused can be retried. A run that fails after its retries moves the row to `failed`. A run that is cancelled in Inngest leaves it in `sending`, which keeps the campaign `sending`; pause and resume it (MCP `campaigns_resume` puts `sending` rows back to `queued`).

Deleting a campaign (UI or MCP `campaigns_delete`) sends `campaigns/deleted` with its `campaignId`. That event cancels `campaign-schedule-send` and `campaign-process-follow-up` runs still sleeping for the campaign (`cancelOn`). A run that wakes anyway skips a deleted campaign.

Rescheduling a campaign sends `campaigns/schedule` again. The new event cancels the older `campaign-schedule-send` run for the same `campaignId` and starts a new one, so only the latest scheduled time sends.

Pausing a campaign (UI or MCP `campaigns_pause`) sends `campaigns/paused` with its `campaignId`, which cancels sleeping `campaign-schedule-send` and `campaign-process-follow-up` runs. MCP `campaigns_resume` sends `campaigns/send-now`, which fans out step 0 again and schedules every follow-up again, counted from the resume time. `campaign-send-step` only sends a `queued` or `failed` send, so the resume sends the queued ones and retries the failed ones (the mail did not go out); `sent`, `delivered` and `bounced` are finished and are skipped. A send already fanned out before the pause still skips a paused campaign.

### Scheduled

| Function id | Cron (UTC) | What it does |
| --- | --- | --- |
| `email-sync-all` | `*/15 * * * *` | Queues sync for all email accounts |
| `crm-google-calendar-sync-all` | `*/15 * * * *` | Queues sync for all calendar connections |
| `report-send-scheduled` | `*/15 * * * *` | Sends scheduled reports that are due |
| `crm-kill-rule` | `0 6 * * *` | Closes stale opportunities |
| `crm-recycle-targets` | `30 6 * * *` | Recycles targets whose sequence ended |
| `crm-renewal-reminders` | `0 7 * * 1` | Creates renewal reminder tasks |
| `ecb-sync-exchange-rates` | `0 17 * * 1-5` | Fetches ECB exchange rates |

Plugin functions are added at runtime with ids `plugin-<id>-cron-<slug>`, `plugin-<id>-on-<slug>` and `plugin-<id>-after`.

## Add a function

<Steps>
<Step>

### Write the function

Create a file in `inngest/functions/`. The SDK is Inngest v4: triggers go in the options object.

```ts
// inngest/functions/crm/notify-big-deal.ts
import { inngest } from "@/inngest/client";
import { prismadb } from "@/lib/prisma";

export const notifyBigDeal = inngest.createFunction(
  { id: "crm-notify-big-deal", name: "Notify big deal", triggers: [{ event: "crm/opportunity.saved" }] },
  async ({ event, step }) => {
    const { record_id } = event.data as { record_id: string };

    const opp = await step.run("load", () =>
      prismadb.crm_Opportunities.findUnique({ where: { id: record_id, deletedAt: null } }),
    );
    if (!opp) return { skipped: "not found" };

    await step.run("notify", async () => {
      // ...
    });
    return { ok: true };
  },
);
```

Use `step.run()` around each side effect. Inngest retries a failed step without repeating the steps that already succeeded. Use a cron trigger (`triggers: [{ cron: "0 6 * * *" }]`) for scheduled work.

</Step>
<Step>

### Register it

Import the function in `app/api/inngest/route.ts` and add it to the `functions` array. A function that is not listed there never runs.

</Step>
<Step>

### Send the event

```ts
import { inngest } from "@/inngest/client";

void inngest.send({ name: "crm/opportunity.saved", data: { record_id: opportunity.id } });
```

Server actions usually send without awaiting (`void`) so the user does not wait. Await the send when the caller must know it was queued.

</Step>
</Steps>

## Conventions

- **Event names:** `<area>/<subject>.<verb>`, for example `crm/account.saved` or `enrich/target.run`.
- **Payloads:** keep them small. Send IDs (`record_id`), not records, and load fresh data in the function.
- **Function ids:** stable and unique. Renaming an id creates a new function in Inngest.
- **Idempotency:** functions can run more than once. The embedding functions, for example, compare a content hash and skip unchanged records.
- **Auth:** functions run without a user session. If the work must respect a user's permissions, pass the user id in the event (the enrichment events use `triggeredBy`) and check it in the function.
- **The `crm/<entity>.saved` events:** sent after creates and updates of accounts, contacts, leads and opportunities. Embeddings and plugin `on` handlers listen to them. Send the event from any new code path that writes these records.

## Production

In production the app needs `INNGEST_EVENT_KEY` and `INNGEST_SIGNING_KEY` from Inngest Cloud, or a self-hosted Inngest server with `INNGEST_BASE_URL`. The Docker Compose stack runs its own Inngest container. See the [configuration reference](/docs/admins/configuration).
